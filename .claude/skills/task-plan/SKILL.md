# タスク計画・検証スキル

目標を受け取り、戦略全体との整合性を確認しながらタスク分解を行い、抜け漏れを検証した上で提案する。

## 引数
- `$ARGUMENTS` = 達成したい目標（例: `/task-plan 町民会館でAI体験会を開催する`）
- 空の場合はユーザーに目標の入力を求めて終了する

## 手順

### 1. 現状の読み込み（並列で実行）
以下を読み込んで全体像を把握する:
- `github_sim3/STRATEGY.md` — 戦略全体の方向性・KPI
- `github_sim3/issues.yaml` — 既存タスクツリーとステータス
- 直近のgitログ（`git log --oneline -10`）— 最近の活動の流れ

### 2. 目標の位置づけ分析
以下を明確にする:
- **戦略との紐づけ**: この目標はどの戦略・カテゴリに属するか？
- **KPIとの関連**: この目標の達成はどのKPIに貢献するか？
- **タイムライン**: 戦略上のフェーズと現在の進捗から、着手タイミングは適切か？
- **前提条件**: この目標を達成する前に完了すべき既存タスクは何か？

### 3. タスク分解（5つの検証観点付き）

目標をタスクに分解する際、以下の **5つの検証観点** を必ずチェックする:

#### ✅ 観点1: 前提条件の充足
- このタスクを始めるために必要な情報・成果物・スキルは何か？
- それらは既存タスクでカバーされているか？
- カバーされていなければ、先行タスクとして追加が必要

#### ✅ 観点2: タスクの粒度
- 各タスクは「1人が1-3日で完了できる」サイズか？
- 大きすぎるタスクはさらに分解する
- 小さすぎるタスク（1時間以下）はsubtasksとしてタスク内に含める

#### ✅ 観点3: 順序の論理性
- タスクの実行順序に論理的な飛躍がないか？
- A→B→Cの間に「暗黙のステップ」が隠れていないか？
- 例: 「イベント企画」→「イベント開催」の間に「告知・集客」が抜けていないか？

#### ✅ 観点4: 既存タスクとの重複・矛盾
- 同じ目的の既存タスクがすでに存在しないか？
- 既存タスクの成果物を活用できないか？
- 既存タスクの方向性と矛盾していないか？

#### ✅ 観点5: 成果物・完了条件の明確性
- 各タスクの完了条件（successCriteria）は具体的か？
- 「○○する」ではなく「○○が存在する/○○が確認できる」のように検証可能か？
- 成果物（outputs）は何か？

### 4. 検証結果の提示

以下の形式でユーザーに提示する:

```
## 🎯 目標: {$ARGUMENTS}

### 戦略上の位置づけ
- 所属: 戦略{N} > カテゴリ{X} > Issue{XX}
- KPI貢献: {該当KPI}
- 前提タスク: {完了済み/未完了のリスト}

### 提案タスク一覧
| # | タスクID | タイトル | 前提 | 完了条件 |
|---|---------|---------|------|---------|
| 1 | {ID} | {タイトル} | なし | {条件} |
| 2 | {ID} | {タイトル} | #1完了後 | {条件} |

### 検証結果
| 観点 | 判定 | 詳細 |
|------|------|------|
| 前提条件 | ✅/⚠️/❌ | {説明} |
| タスク粒度 | ✅/⚠️/❌ | {説明} |
| 順序の論理性 | ✅/⚠️/❌ | {説明} |
| 重複・矛盾 | ✅/⚠️/❌ | {説明} |
| 完了条件の明確性 | ✅/⚠️/❌ | {説明} |

### ⚠️ 指摘事項（あれば）
- {具体的な問題点と修正提案}

### 💡 推奨事項（あれば）
- {より良くするための提案}
```

### 5. ユーザー確認
- 提案内容をユーザーに確認する
- 修正要望があれば反映する
- 承認されたら「`/task-create {ID} {タイトル}` で各タスクを作成してください」と案内する
- **このスキルではタスクの実際の作成は行わない**（確認後にユーザーが /task-create を実行する）
